# Consensus Orchestrator API (Experimental)

!!! warning "Experimental Feature"
    The Orchestrator API (`MassFlow.models` and `MassFlow.consensus`) is an experimental architectural foundation introduced in MassFlow v1.0. It is **not** currently integrated into the stable `massflow annotate` CLI workflow.

    This API was built specifically to prepare the repository for the upcoming v1.1 release, which will allow a separate satellite repository (`massflow-ml`) to plug heavy machine learning models (like MS2DeepScore) into the core pipeline without forcing dependency bloat (e.g., PyTorch, TensorFlow) onto the main MassFlow installation.

---

## The Vision

When identifying unknown metabolites, different algorithms look at different chemical features. A classical `cosine` algorithm is excellent at aligning exact mass fragments, while a deep learning model like `ms2deepscore` is better at recognizing structural similarity even when fragmentation patterns differ.

The **Consensus Orchestrator** is designed to execute a "Map-Reduce" style pattern:
1.  Run a query spectrum through multiple, independent similarity engines.
2.  Gather all the resulting hits.
3.  Group the hits by the candidate's unique identifier (e.g., `reference_id` or `inchikey`).
4.  Calculate a weighted consensus score for each candidate.
5.  Apply intelligent tie-breaking and scientific credibility checks to select the true "best" annotation.

---

## Data Contracts (`MassFlow.models`)

To keep MassFlow's core lightweight, the orchestrator relies entirely on strictly typed Pydantic data contracts to communicate with external ML satellites. It does not parse raw `matchms.Spectrum` objects.

### `AnnotationHit`
The atomic unit of an annotation result. Every engine (whether local or remote) must return hits in this exact shape:

*   `engine_id`: Identifier for the engine (e.g., `"cosine"`, `"ms2deepscore"`).
*   `reference_id`: Unique identifier for the candidate compound.
*   `score`: The similarity score (typically `0.0` to `1.0`).
*   `rank`: The rank of this hit within the specific engine's result set.
*   `inchikey`: (Optional) For structure-level aggregation.
*   `smiles`: (Optional) For downstream visualization.

### `ConsensusInput`
The payload handed to the orchestrator for a single query spectrum.

*   `query_id`: The ID of the experimental spectrum.
*   `hits`: A flat list of every `AnnotationHit` generated by all configured engines for this query.

### `ConsensusResult`
The final, orchestrated output.

*   `query_id`: The ID of the experimental spectrum.
*   `best_reference_id`: The winning candidate.
*   `best_consensus_score`: The final aggregated score.
*   `flagged_for_review`: A boolean indicating if the top engines violently disagreed (see Scientific Credibility below).
*   `candidates`: A sorted list of all evaluated candidates and their sub-scores.

## Orchestration Logic (`MassFlow.consensus`)

The `ConsensusEngine` is a pure-Python, dependency-free class that handles the math and logic of resolving a `ConsensusInput`.

### 1. Weighted Scoring

You configure the engine with a `ConsensusConfig` object that maps engine IDs to their relative weights.

```python
from MassFlow.models import ConsensusConfig
from MassFlow.consensus import ConsensusEngine

config = ConsensusConfig(
    engine_weights={"cosine": 0.6, "ms2deepscore": 0.4},
    tie_breaker_strategy="highest_rank"
)
engine = ConsensusEngine(config)
```

The engine calculates the final score as:
$$ Score_{consensus} = \frac{(Score_{cos} \cdot 0.6) + (Score_{deep} \cdot 0.4)}{1.0} $$

**Missing Data Tolerance:** If an engine completely fails to find a candidate that another engine identified, its score is gracefully treated as `0.0`.

### 2. Tie-Breaking Strategies

If two candidates end up with the exact same consensus score, the engine applies a configured `tie_breaker_strategy`:

*   `highest_rank`: The winner is the candidate with the lowest (best) sum of ranks across all engines. Missing ranks are penalized.
*   `average_score`: The winner is the candidate with the highest unweighted average score.
*   `validator_engine`: The winner is chosen based purely on the score from a designated trusted engine (e.g., always trust the `cosine` score to break a tie).

### 3. Scientific Credibility Check

A simple weighted average is scientifically dangerous if the underlying models violently disagree. For example, if Engine A thinks Caffeine is the #1 hit, but Engine B ranks Caffeine at #500, averaging their scores masks a fundamental algorithmic discordance.

The `ConsensusEngine` explicitly evaluates this. If an engine's #1 hit is ranked worse than the `flag_rank_discrepancy_threshold` (default: 5) by any other configured engine, the `ConsensusResult` is flagged for manual expert review.

## Triage Bitmasking (`triage_flags`)

Heavy ML engines are computationally expensive. To optimize routing, MassFlow v1.0 implements a fast `numpy`-based scan during the `massflow db build` step.

If a spectrum contains a specific diagnostic fragment (e.g., the Tyrosine immonium ion at `136.076` Da), MassFlow appends a `{"has_tyrosine_fragment": true}` JSON flag to the `triage_flags` column in the SQLite database.

When the v1.1 orchestrator is fully integrated, it will use these bitmasks to route only the relevant spectra to the heavy ML satellite, saving significant GPU cycles.
